# 知无不言站点经验

## 平台特征

- 讨论详情页使用 `/question/<数字ID>`。公开静态页面通常能返回标题、问题正文和“N 个回复”数量，但顶层回答正文可能由登录态页面动态加载；看到回复数量不等于已经取得回复内容。
- 登录后的详情页同时包含顶层回答和回答下的楼中楼评论。楼中楼常出现数月或数年后的处理结果、反例和对服务商意见的质疑，分析实际卖家经验时不能省略。
- 页面上的“回复数”、实际顶层回答数和楼中楼评论数是不同口径。删除、隐藏或页面状态也可能让显示数与可提取数不一致。

## 有效模式

1. 公开搜索或站内搜索只负责发现候选 `/question/<ID>` 原帖。用户只要问题正文时，静态内容足够即可停止。
2. 用户需要回答、评论、后续反馈或讨论分析时，直接按“需要登录态”处理并打开 Codex 内置浏览器；不要把静态页显示的回复数量当作已取得回答，也不必先对每篇帖子尝试静态读取。
3. 登录态默认使用 Codex 内置浏览器。它明确未登录时，按主 skill 说明实际原因，再自动回退实际配置的本地浏览器 Profile。若本地浏览器也明确要求登录，请用户手动登录后继续读取。默认路由下不要停在“评论不可见”，也不要要求用户先在内置浏览器重新登录。用户显式指定内置浏览器时，遵循主 skill 的显式浏览器例外。
4. 在登录页面中先读取完整 DOM snapshot。当前验证可用的结构提示如下，但只能作为可能变化的定位线索：
   - 顶层回答容器：`div.aw-item[id^="answer_list_"]`
   - 顶层回答正文：回答容器内的 `.markitup-box`
   - 楼中楼容器：`.aw-comment-box .aw-comment-list`
   - 单条楼中楼评论：`.aw-comment-list li`
5. 每篇帖子分别记录：页面标示回复数、实际顶层回答数、实际楼中楼评论数、帖子日期，以及与结论直接相关的原话。显示数量与提取数量不一致时保留差异，不强行补齐。
6. 回答者简介出现“检测认证”、电话、微信、实验室、服务商或广告性签名时，标为潜在商业利益来源；仍可引用其事实陈述，但不能仅凭身份提高可信度。第一手卖家案例应尽量包含触发原因、提交材料、申诉次数和最终结果。
7. 排序、展开或翻页优先点击页面实际生成的控件或使用其完整链接，不自行拼接参数。只读调研不得操作回复编辑器、关注、点赞、举报或发布按钮。

## 完成标准

- 用户要“看帖子”：取得标题、问题正文和日期即可。
- 用户要“看回复/评论”：至少确认顶层回答正文已出现；存在非零楼中楼计数时还要读取对应楼中楼评论。
- 用户要“分析讨论”：在上述内容基础上区分第一手卖家、推测性意见、服务商观点和后续结果，并说明样本数量、年代与主要分歧。

## 已知陷阱

- 静态页面或搜索摘要出现“15 个回复”等数字，但没有任何回答正文：这是未完成，不是无评论。
- DOM snapshot 中的“评论”可能同时指问题评论、顶层回答以及回答下的楼中楼；汇总时必须分开计数。
- 登录后可能出现回复编辑器和用户账号信息。它们只证明登录有效，不得读取会话数据，也不得在只读任务中输入或提交内容。
- 老帖中的 Amazon 界面、政策名称和审核路径可能已变化；用日期限定结论，不把旧案例直接写成当前政策。
